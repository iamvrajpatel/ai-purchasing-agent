# Agent Behaviour

This document maps the assignment's expected agent behaviours to the implemented purchasing-agent system.

| Agent Behaviour | Status | How Implemented |
| --- | --- | --- |
| Determine what information the agent needs | Implemented | The agent and deterministic services use recommendation details, product SKU/name/id, warehouse id/name, inventory, demand forecasts, timely incoming POs, supplier catalog rows, budget, storage capacity, supplier availability, approval state, purchase orders, supplier responses, validations, and recovery cases. |
| Determine what tools or APIs it should use | Implemented | The backend exposes a restricted tool registry for product details, inventory, demand forecast, sales history, open POs, supplier options, supplier conditions, budget, storage capacity, purchase requirement calculation, purchase constraint evaluation, PO details, supplier confirmation outcome, shortfall calculation, alternate suppliers, and current requirement after confirmation. |
| Determine what data should exist | Implemented | PostgreSQL stores products, warehouses, inventory, forecasts, sales, suppliers, `supplier_products`, budgets, recommendations, agent runs, tool calls, events, validations, approvals, purchase orders, and recovery cases. Demo data includes Scenario 1 replenishment, split sourcing, partial supplier fulfillment, supplier shortage, budget pressure, storage pressure, and lead-time cases. |
| Determine how the agent should interact with tools | Implemented | The LLM can call only registered backend tools. `ToolExecutor` filters arguments, executes tools through the registry, persists inputs/outputs in `agent_tool_calls`, and records timeline events in `agent_events`. The backend rejects arbitrary tool access and does not allow arbitrary SQL. |
| Determine how decisions should be made | Implemented | The LLM investigates and explains, but deterministic backend services decide the final safe action. `DecisionEngine` calculates requirements, chooses single-supplier or split-supplier proposals, rejects unnecessary purchases, or returns investigation when constraints block all feasible options. |
| Determine what actions the agent should be allowed to perform | Implemented | The agent can propose purchasing actions only. It cannot approve, execute, or directly create purchase orders. Purchase orders are created only by backend execution services after approval and current-state revalidation. |
| Determine when human approval may be appropriate | Implemented | Approval requests are created for high-value proposals, split supplier proposals, and recovery/supplemental purchase actions. Approvals use server-controlled buyer identity, and split proposals are approved and executed independently per supplier action. |
| Determine how the result should be validated | Implemented | `ValidationService` validates the pre-execution decision, persisted purchase order fields, and supplier outcome. Partial confirmation or mismatched supplier results mark the PO as failed and create recovery/escalation records. |
